# Task 011 — источники, ёмкость и оставшиеся условия эксплуатации

Дата: 16.10.2026. Базовая рабочая версия: `0a51ee334fa4b1c2f6711047d258580487d21720`.

## Границы проверки

Исходные `okrug` и `raion` обследованы командами `SELECT` через проверенный
SSH и локальный shared-memory SQL transport. Позже пользователь отдельно
разрешил создание нового технического SQL-читателя: изменены только новые
security principals и их права, как описано ниже. Существующие записи, таблицы,
исходные файлы, режим аутентификации и AD не изменялись. Legacy database manager
не импортировался.
Приватные отчёты хранятся отдельно; реальные пути, личности, номера карточек,
значения исторических номеров и содержимое документов в Git не публикуются.

Диагностический оператор имеет `sysadmin`. Поэтому первоначальные команды чтения
**не доказывают** серверный запрет записи migration-reader учётной записи.
Отдельный SQL-читатель затем проверен под собственным логином.
`ApplicationIntent=ReadOnly` не заменяет проверку эффективных прав.
Закрытые профили чтения остаются отключёнными, `confirm_readonly=false`.

## Исторические номера и совместимость

`reg_number` — регистрационный номер; `number` в существующей форме ACTI v2 —
**номер публикации / газеты**. Их нельзя объединять или использовать общий максимум.
В `reg_number` все непустые значения состоят из ASCII-цифр: 5 769 в `okrug`
и 107 305 в `raion`; в `okrug` два значения отсутствуют. Исходное строковое
значение, включая ведущие нули, должно сохраняться.

Полные максимумы `reg_number` подтверждены агрегированным SQL и независимым
полным чтением проекций номера/даты/ID. Закрытый отчёт содержит 125
предварительных групп регистрации по типу/периоду и отдельно 125 групп
публикации. Повторы выявлены; сами значения и связанные ID остаются закрытыми.
Сам по себе числовой `MAX` не задаёт безопасную выдачу: требуется подтвердить
серию, тип и период. Существующий запрет новой выдачи исторических номеров
в `number_binding.py` сохраняется. Номер публикации содержит составные значения;
это отдельный реквизит, а не ошибка регистрационной последовательности.

Подготовлено проектное сопоставление **130/130 исходных столбцов** (65 в каждой
базе), включая все 26 столбцов карточки, справочники, junctions и служебное
происхождение. Все **25 полей** встроенной конфигурации ACTI v2 учтены.
Это покрытие предложенными правилами, а не выполненный импорт или назначенные
target UUID. Реальных mapping/run/attempt записей этот этап не создаёт.

Для 71 NULL-заголовка требуется явная политика переноса: рабочая форма требует
заголовок. В пяти заголовках `okrug` длина превышает 1 000 UTF-16 единиц
(максимум 1 967); это сигнал проверки лимита формы, а не доказанное превышение
Python code-point length. Значений страниц/приложений вне пределов формы и
результатов исполнения длиннее 100 000 единиц не найдено. При этом в `raion`
есть 1 357 NULL страниц и 66 541 NULL приложений — их нельзя молча заменить
значениями по умолчанию. Одна непустая дата публикации не разобрана; остальные
проверенные непустые даты распознаны утверждёнными форматами, без догадок locale.

Boolean-профиль полностью классифицирован: кроме SQL NULL и «Да»/«Нет»/
«Не указано», встречаются точные строковые варианты `0.0` и `1.0`. Это не
свободный текст и не основание считать любую непустую строку true. Для Task 012
подготовлено предложение закрытого словаря нормализации с обязательным
сохранением исходного значения; произвольные числовые приведения не разрешены.
Исходные записи не исправляются. Часовой пояс исторического `datetime2`
нельзя присваивать по умолчанию без отдельного подтверждения provenance.

## Согласованный SQL-читатель — APPLIED_VERIFIED

По отдельному явному разрешению пользователя создан **один новый SQL login и
по одному пользователю в двух БД**. Доступ ограничен SELECT на 14 перечисленных
таблицах каждой базы: без административных ролей, `db_datareader`, schema-wide
SELECT и автоматического доступа к будущим таблицам. Для этого же нового
пользователя явно запрещены INSERT/UPDATE/DELETE/EXECUTE и изменение схемы/
создание объектов/изменение прав. SQL authentication уже была включена; её режим
не менялся. Новые AD/Windows-пользователи не создавались.

До применения проверены отсутствие одноимённых principals и совпадающих SID,
точный набор таблиц и унаследованные public grants. Создание выполнено одной
транзакцией; повторное создание или принятие чужой учётки блокируется. Закрытая
квитанция фиксирует proposal hash, pinned SID, фактические даты создания и права.
Пароль сгенерирован отдельно, не находился в Git, аргументах процесса или
публичном выводе; локальный ACL допускает текущего оператора и SYSTEM.

Две **настоящие SQL-auth connections**, без `EXECUTE AS`, подтвердили точные
ORIGINAL_LOGIN/SID, отсутствие административных ролей, отрицательные DML/DDL/
EXECUTE effective permissions, SELECT по всем 28 объектам и реальный COUNT_BIG
карточек. Проверочные записи/DDL не выполнялись. Транспорт — локальный shared
memory внутри проверенного SSH, без открывания TCP-порта или обхода TLS-проверки.

Закрытая конфигурация получила credential/proof references. Root-only копия
секрета и квитанции помещена в конфигурационный escrow ACTI, включаемый в
существующий зашифрованный внешний backup; API и worker этот каталог не получают.
Ручная ротация пароля требуется не позднее **14.01.2027**.

Это приёмка **SQL-прав**, а не всего канала миграции: read-only доступ к оригиналам
и конечная конфигурация execution host ещё не приняты. Поэтому общий профиль
источников по-прежнему отключён; миграция не запускалась.

Запас должен учитывать версии. Для сравнения, 1 / 3 / 5 / 10 полных поколений
измеренного набора занимают примерно 4,47 / 13,41 / 22,34 / 44,69 ГиБ.
Это расчётные сценарии, **не новая политика версионирования**.
Для существующего retention last 3 + daily 14 + weekly 8 + monthly 12
консервативный предел — 37 snapshots до учёта пересечений и дедупликации.
37 независимых копий одних оригиналов занимают около 165,35 ГиБ; при пяти
поколениях — около 826,73 ГиБ, при десяти — около 1 653,45 ГиБ.
Это только файловая часть: PostgreSQL, WAL, настройки, служебные расходы и
будущий рост прибавляются отдельно. Restic обычно хранит повторяющиеся блоки
совместно, но неизвестную степень дедупликации нельзя принимать за гарантию.

Размер новой PostgreSQL с реальными индексами, извлечённым содержимым и версиями
этим расчётом не доказан. Прежний синтетический пилот на 150 000 карточек занимал
404 642 839 байт БД; это измерение синтетического корпуса, не прогноз миграции.
Перед снятием GO/NO-GO необходимо сохранить контролируемый запас и наблюдать рост.

синтетических документов учтены отдельно от зависшей очереди.
