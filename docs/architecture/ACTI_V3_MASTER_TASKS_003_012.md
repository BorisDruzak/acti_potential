## 0. Цель, границы и порядок

ACTI v3 должна стать **готовой универсальной системой организационных документов и процессов**, на которой администратор самостоятельно создаёт реестры, формы, справочники и описания процессов. Редактор ведёт данные и экземпляры процессов, читатель просматривает разрешённую информацию. Миграция из существующих SQL Server `okrug` и `raion` выполняется **после готовности функционального ядра**, а не вместо его проектирования.

Task 001 (платформенное ядро) и Task 002 (базовый schema engine, карточки, ACL, три интерфейса) считаются завершёнными по соответствующим приёмкам. Повторно создавать их нельзя. Этот документ — один канонический последовательный список дальнейших задач; не создавать второй противоречащий backlog или по отдельному огромному плану для каждого подпункта.

### Неизменяемые архитектурные правила

1. **Одна ACTI Core:** сохранять текущие FastAPI + SQLAlchemy/Alembic + PostgreSQL + React + Docker Compose, платформенные роли, audit/outbox, `StorageProvider`, разделение `/admin`, `/work`, `/view`. Не строить новые изолированные подсистемы там, где уже есть общая модель.
2. **Конструктор — источник поведения:** для произвольного нового типа документа/процесса не требуется создавать отдельную SQL-таблицу или React-форму. Поведение, условия, справочники и права проверяет backend; frontend отображает ту же опубликованную версию конфигурации.
3. **Схема ACTI v2 — обычная конфигурация:** 25 бизнес-полей, шесть разделов, два реестра, десять справочников на реестр; нельзя превращать её в привилегированный hardcoded путь. Исторические реквизиты и значение `NULL` сохраняются.
4. **Права по умолчанию закрыты:** роль администратора конфигурации не даёт автоматического доступа к содержимому; ACL действуют на поиск, выдачу, API, файлы, историю, экспорт, процессы, события и будущие интеграции. Не раскрывать скрытые значения косвенно через число результатов, условия, автоподстановку или логи.
5. **Жизненный цикл данных:** стабильные UUID; опубликованные версии неизменяемы; старые значения, файлы, утверждённые основания и номера не перезаписываются. Изменения сопровождаются автором, временем, причиной при необходимости, аудитом и событиями.
6. **SQL Server только источник:** обе рабочие базы и оригиналы открываются исключительно через read-only адаптер. Не вызывать legacy-менеджеры, которые могут выполнить DDL/seed или создать каталоги. Массового импорта до Task 012 **нет**. Секреты, адреса, пути, персональные данные и реальные документы не публиковать в Git.
7. **AD поздно:** до Task 011 локальная авторизация и существующие UUID/роли; OIDC/AD не внедрять раньше.
8. **Развёртывание:** существующая Ubuntu VM, два обязательных тома (`/srv/acti/postgresql` и `/srv/acti/documents`), проверка mount/UUID, отдельные роли БД и закреплённые образы. Не переразмечать диски, не ослаблять TLS, не выкладывать PostgreSQL/Redis в LAN.
9. **Без формальных остановок:** Codex самостоятельно реализует пункты утверждённой задачи, исправляет обнаруженные ошибки, запускает необходимые проверки и браузерные сценарии. Не вводить обязательные независимые аудиты, многоступенчатые ревью, повторные полные CI и evidence-пакеты для обычной функциональности. Безопасность существующих слоёв не ослаблять.
10. **Без ложного PASS:** фактическая проверка в браузере, с БД и с реальным HTTPS API обязательна. Когда недоступны браузер, ВМ, сертификаты или требуемые зависимости, честно указать `BLOCKED` и причину; нельзя заменять реальное выполнение моками или одним `npm build`.

## Task 004 — Реестр регистрационных номеров и резервирование

**Задача:** реализовать **самостоятельный доменный реестр номеров (книгу регистрации)**, связанный с создаваемыми администратором реестрами и документами. Это не подмена существующего Registry и не просто автозаполнение текстового `reg_number`.

### Модель и инварианты

1. `NumberSeries` — настраиваемая серия/журнал: имя, код, связанный реестр, допустимые типы, необязательная организационная область, период (например, календарный год), начало/шаг, маска/префикс/суффикс, зона времени/граница периода, статус, правила резервирования, права. Нельзя предполагать, что `okrug` и `raion` имеют одну нумерацию или что все виды документов делят общий счётчик.
2. `NumberEntry` (или эквивалент) — отдельная неизменяемая идентичность присвоенного порядкового числа с сериализованным отображением. Ключ уникальности — `series_id + period_key + ordinal`, дополнительно проверять уникальность сформированного номера **в пределах серии/периода**. Не устанавливать глобальный `UNIQUE(reg_number)` на исторические карточки: у разных журналов и источников возможны совпадения.
3. `NumberReservation`/`NumberOperation` — журнал резервов, выдачи, привязки к документу, отмены, истечения срока, признания недействительным; actor, timestamp, reason, source, idempotency key, при необходимости срок/получатель/документ. Предусмотреть статусы `reserved`, `assigned`, `cancelled`, `expired`, `void` и отдельно historical/imported для миграции, если необходимо.
4. **Резерв не равен зарегистрированному документу.** Редактор резервирует один номер или ограниченный последовательный диапазон на понятный срок (или бессрочно согласно настройке), затем привязывает номер к документу. Срок резервирования, лимиты и допустимые действия задаются администратором — не изобретать безусловную автоматическую отмену.
5. **Номер не выдаётся повторно по умолчанию** после отмены, истечения, ошибки или удаления карточки. Сохраняется аудируемая запись с причиной, а счётчик не откатывается. Любая иная юридически допустимая политика повторного использования возможна только как явная отдельная настройка и после проверки правил организации; в MVP оставить непереиспользование.
6. Атомарная выдача: транзакционная блокировка строки серии/периода или эквивалент PostgreSQL, ограничения БД и идемпотентность запроса. Два параллельных пользователя не получают одинаковый номер; повтор HTTP-запроса не тратит новый номер; выдача пачки либо целиком фиксируется, либо целиком откатывается.
7. **Legacy-совместимость:** историческое `reg_number` ACTI v2 — исходная строка, не переписывать и не считать её автоматически подтверждённой новой выдачей. Для будущего импорта нужны provenance и режим записи исторических номеров без перераспределения; неоднозначные/повторные номера сохранять с отдельной классификацией.
8. **До Task 012 запрещать рабочую выдачу в исторически занятых сериях без проверки фактических максимальных номеров обеих SQL Server.** Для пилота использовать отдельные синтетические серии. В Task 011/012 на основании read-only профиля определить политику продолжения: новая серия/период, начальная граница или сохранение legacy как отдельного журнала; не создавать коллизии.

4. Сроки и простые статусы: ожидается/в работе/просрочено/завершено/приостановлено. Необязательная фоновая актуализация просрочек через существующий worker и audit/outbox.
