## 0. Цель, границы и порядок

ACTI v3 должна стать **готовой универсальной системой организационных документов и процессов**, на которой администратор самостоятельно создаёт реестры, формы, справочники и описания процессов. Редактор ведёт данные и экземпляры процессов, читатель просматривает разрешённую информацию. Миграция из существующих SQL Server `okrug` и `raion` выполняется **после готовности функционального ядра**, а не вместо его проектирования.

Task 001 (платформенное ядро) и Task 002 (базовый schema engine, карточки, ACL, три интерфейса) считаются завершёнными по соответствующим приёмкам. Повторно создавать их нельзя. Этот документ — один канонический последовательный список дальнейших задач; не создавать второй противоречащий backlog или по отдельному огромному плану для каждого подпункта.

### Неизменяемые архитектурные правила

1. **Одна ACTI Core:** сохранять текущие FastAPI + SQLAlchemy/Alembic + PostgreSQL + React + Docker Compose, платформенные роли, audit/outbox, `StorageProvider`, разделение `/admin`, `/work`, `/view`. Не строить новые изолированные подсистемы там, где уже есть общая модель.
2. **Конструктор — источник поведения:** для произвольного нового типа документа/процесса не требуется создавать отдельную SQL-таблицу или React-форму. Поведение, условия, справочники и права проверяет backend; frontend отображает ту же опубликованную версию конфигурации.
3. **Схема ACTI v2 — обычная конфигурация:** 25 бизнес-полей, шесть разделов, два реестра, десять справочников на реестр; нельзя превращать её в привилегированный hardcoded путь. Исторические реквизиты и значение `NULL` сохраняются.
4. **Права по умолчанию закрыты:** роль администратора конфигурации не даёт автоматического доступа к содержимому; ACL действуют на поиск, выдачу, API, файлы, историю, экспорт, процессы, события и будущие интеграции. Не раскрывать скрытые значения косвенно через число результатов, условия, автоподстановку или логи.
5. **Жизненный цикл данных:** стабильные UUID; опубликованные версии неизменяемы; старые значения, файлы, утверждённые основания и номера не перезаписываются. Изменения сопровождаются автором, временем, причиной при необходимости, аудитом и событиями.
6. **SQL Server только источник:** обе рабочие базы и оригиналы открываются исключительно через read-only адаптер. Не вызывать legacy-менеджеры, которые могут выполнить DDL/seed или создать каталоги. Массового импорта до Task 012 **нет**. Секреты, адреса, пути, персональные данные и реальные документы не публиковать в Git.
7. **AD поздно:** до Task 011 локальная авторизация и существующие UUID/роли; OIDC/AD не внедрять раньше.
8. **Развёртывание:** существующая Ubuntu VM, два обязательных тома (`/srv/acti/postgresql` и `/srv/acti/documents`), проверка mount/UUID, отдельные роли БД и закреплённые образы. Не переразмечать диски, не ослаблять TLS, не выкладывать PostgreSQL/Redis в LAN.
9. **Без формальных остановок:** Codex самостоятельно реализует пункты утверждённой задачи, исправляет обнаруженные ошибки, запускает необходимые проверки и браузерные сценарии. Не вводить обязательные независимые аудиты, многоступенчатые ревью, повторные полные CI и evidence-пакеты для обычной функциональности. Безопасность существующих слоёв не ослаблять.
10. **Без ложного PASS:** фактическая проверка в браузере, с БД и с реальным HTTPS API обязательна. Когда недоступны браузер, ВМ, сертификаты или требуемые зависимости, честно указать `BLOCKED` и причину; нельзя заменять реальное выполнение моками или одним `npm build`.

## Task 004 — Реестр регистрационных номеров и резервирование

**Задача:** реализовать **самостоятельный доменный реестр номеров (книгу регистрации)**, связанный с создаваемыми администратором реестрами и документами. Это не подмена существующего Registry и не просто автозаполнение текстового `reg_number`.

### Модель и инварианты

1. `NumberSeries` — настраиваемая серия/журнал: имя, код, связанный реестр, допустимые типы, необязательная организационная область, период (например, календарный год), начало/шаг, маска/префикс/суффикс, зона времени/граница периода, статус, правила резервирования, права. Нельзя предполагать, что `okrug` и `raion` имеют одну нумерацию или что все виды документов делят общий счётчик.
2. `NumberEntry` (или эквивалент) — отдельная неизменяемая идентичность присвоенного порядкового числа с сериализованным отображением. Ключ уникальности — `series_id + period_key + ordinal`, дополнительно проверять уникальность сформированного номера **в пределах серии/периода**. Не устанавливать глобальный `UNIQUE(reg_number)` на исторические карточки: у разных журналов и источников возможны совпадения.
3. `NumberReservation`/`NumberOperation` — журнал резервов, выдачи, привязки к документу, отмены, истечения срока, признания недействительным; actor, timestamp, reason, source, idempotency key, при необходимости срок/получатель/документ. Предусмотреть статусы `reserved`, `assigned`, `cancelled`, `expired`, `void` и отдельно historical/imported для миграции, если необходимо.
4. **Резерв не равен зарегистрированному документу.** Редактор резервирует один номер или ограниченный последовательный диапазон на понятный срок (или бессрочно согласно настройке), затем привязывает номер к документу. Срок резервирования, лимиты и допустимые действия задаются администратором — не изобретать безусловную автоматическую отмену.
5. **Номер не выдаётся повторно по умолчанию** после отмены, истечения, ошибки или удаления карточки. Сохраняется аудируемая запись с причиной, а счётчик не откатывается. Любая иная юридически допустимая политика повторного использования возможна только как явная отдельная настройка и после проверки правил организации; в MVP оставить непереиспользование.
6. Атомарная выдача: транзакционная блокировка строки серии/периода или эквивалент PostgreSQL, ограничения БД и идемпотентность запроса. Два параллельных пользователя не получают одинаковый номер; повтор HTTP-запроса не тратит новый номер; выдача пачки либо целиком фиксируется, либо целиком откатывается.
7. **Legacy-совместимость:** историческое `reg_number` ACTI v2 — исходная строка, не переписывать и не считать её автоматически подтверждённой новой выдачей. Для будущего импорта нужны provenance и режим записи исторических номеров без перераспределения; неоднозначные/повторные номера сохранять с отдельной классификацией.
8. **До Task 012 запрещать рабочую выдачу в исторически занятых сериях без проверки фактических максимальных номеров обеих SQL Server.** Для пилота использовать отдельные синтетические серии. В Task 011/012 на основании read-only профиля определить политику продолжения: новая серия/период, начальная граница или сохранение legacy как отдельного журнала; не создавать коллизии.

### API и UI

- Админ `/admin`: справочник серий/правил, просмотр журналов, настройка права reserve/assign/cancel/void/view, история операций, поиск занятых/свободных интервалов, выбор формата; создание/блокировка серии.
- Редактор `/work`: «Реестр номеров», запрос следующего номера, резервирование одного/диапазона, список своих и доступных резервов, привязка к документу, отображение статуса и срока. Сохранение номера в карточке через серверную операцию, без возможности подставить произвольное значение вместо выделенного.
- Читатель `/view`: только разрешённый журнал регистрации/сведения о номере и связанном документе; скрывать закрытые документы и персональные служебные поля.
- API с транзакциями, audit/outbox и ACL. Выдача не требует открытия целевого документа по чужим правам. Для полей без подключённой серии сохранить обычное редактирование по существующим правилам; для полей с серией — применять серверную политику.
- Отчёты по использованию: выданные, зарезервированные, присвоенные, погашенные, свободная текущая граница; экспорт только для разрешённых данных.

**Автоматическая проверка в браузере:** администратор создаёт две независимые серии, задаёт формат и права; два редактора одновременно резервируют следующие значения и ограниченный диапазон. Проверить отсутствие дублей, retry одного запроса, привязку к карточке, отмену и неповторную выдачу, переход периода, просмотр журнала читателем, запреты API без прав. После перезапуска значения и последовательность остаются неизменными. Все номера и данные тестовые.

**Критерий результата:** управляемая книга номеров с резервами и юридически прослеживаемой историей, не создающая дубликатов при параллельной работе и не переписывающая архивную нумерацию.

## Task 005 — Извлечение текста, DocumentBlock и полнотекстовый поиск

**Задача:** реализовать этап 4 Roadmap как отдельный надёжный конвейер поверх уже готовых DocumentVersion/DocumentFile и existing worker/outbox.

**Реализация:**

1. Сущности `ContentExtraction` (file/version ID, SHA-256, parser + version, state, timestamps, errors, full text, предупреждения) и `DocumentBlock` (stable ID в пределах версии, тип, порядок, parent, страница при наличии, таблица/абзац/пункт, исходный якорь). Повторный запуск парсера с тем же fingerprint не плодит дубли.

6. Список и карточка документов получают вкладку «Содержание» и единый поисковый интерфейс с фильтрами по реестру, типу, реквизитам и фактическому тексту.
7. OCR сканированных изображений — **отдельное расширение**, как в Roadmap: предусмотреть статус «нет цифрового текстового слоя» и интерфейс подключаемого OCR provider, но не запускать тяжёлый OCR/LLM без решения по качеству и ресурсам.

**Автоматическая проверка в браузере:** редактор загружает синтетические DOCX/PDF с известным русским текстом; после обработки читатель находит фразу по содержимому и близкую строку с опечаткой, видит фрагмент/версию и открывает оригинал. Закрытый документ и скрытое поле не видны ни в результатах, ни в подсказках; повторная обработка идемпотентна, битый файл даёт статус ошибки, но карточка остаётся доступной.

**Критерий результата:** ACTI ищет по реальному цифровому содержимому без LLM и сохраняет структурные источники для будущих ссылок/RAG.

## Task 011 — Эксплуатационная готовность и поздняя интеграция AD

**Задача:** подготовить реализованную ACTI Core к реальному корпусу до миграции. Это **последний** инфраструктурно-интеграционный этап, а не повод откладывать функциональные задачи.

**Реализация:**

1. **AD/OIDC только сейчас:** подключить доступный локальный Identity Provider/AD по согласованной конфигурации. Не заменять стабильный User UUID на логин/SID и не терять локальные роли, ACL, аудит, номера, историю. Явная политика связывания старой локальной и доменной личности, защита от ошибочного слияния по ФИО; оставить аварийную локальную админ-учётную запись.

3. **Внешний backup PostgreSQL и оригиналов**, расписание, retention, мониторинг ошибок, проверяемое восстановление в изолированное окружение. Backup одной ВМ или дамп на том же диске не является внешним. Сделать процедуру отмены неуспешного deploy/миграции.
4. Проверить TLS/доверие/renewal, восстановление после штатного reboot и отказа сервиса, disk mount guard, права файлов, эксплуатационные журналы, очередь фоновой обработки, alerting на критические отказы. Сохранять уже принятые security-инварианты.
5. **Оценить реальную ёмкость**: read-only отчёт по суммарному размеру файлов в `okrug` и `raion`, запас на версии/индексы/бэкапы и доступные 400 ГиБ document storage. При недостатке места не начинать Task 012 до расширения ёмкости — не угадывать нужный объём.
6. Нагрузочный пилот на **синтетическом** корпусе, масштабируемом до ориентира 150 000 карточек и десятков одновременных сессий, с приоритетом search/list/export/ACL и reindex. По замерам настроить индексы, worker batches, соединения, таймауты и память. Не создавать фейковые фикстуры в реальных реестрах и не уничтожать старые данные.
7. Зафиксировать фактические результаты, известные ограничения и автоматические GO/NO-GO условия перед переносом реального корпуса. Не требовать ритуального внешнего security-review вместо проверок по реальному риску.

**Автоматическая проверка в браузере:** реальный AD/OIDC login для тестовой доменной учётной записи (если инфраструктурный доступ имеется), роли admin/editor/viewer, старый локальный резервный admin, ACL/схемы/номера/поиск/процесс; штатный restart/reboot и повторный вход. Отдельно выполнить автоматическое restore-test в изолированной среде и e2e smoke после него. Если AD/внешнее backup или место реально отсутствуют, отметить **BLOCKED** с конкретным отсутствующим ресурсом: нельзя считать готовым к миграции без этих условий.

**Критерий результата:** ACTI готова принимать настоящие данные, а не только демонстрационные, с проверенной идентификацией, сохранностью, ёмкостью и восстановлением.

## Task 012 — Финальная контролируемая миграция SQL Server `okrug` и `raion`

**Задача:** перенести исторические документы и оригиналы **только после PASS задач 003–011** в полностью функционирующую ACTI Core, не переделывая платформу под данные на ходу.

### Исходная точка

При прежнем обследовании сообщалось:

| База | Карточек | Найдено файлов | Отсутствует | Без пути / не классифицировано |
| --- | ---: | ---: | ---: | --- |
| `okrug` | 5 769 | 5 684 | 1 | 84 без пути |
| `raion` | 107 305 | 106 940 | 120 | 245 карточек требуют точной классификации |

**Итого: 113 074 карточки, 112 624 найденных файла, 121 отсутствующий; категории 84/245 не смешивать и не выдавать за подтверждённую полную классификацию.** Перед переносом пересчитать актуальные значения по источникам: рабочие БД могли измениться. Суммарный размер файлов не установлен заранее.

### План реализации

1. Сначала read-only инвентаризация обеих живых SQL Server: реальные PK/типы/NULL, даты, справочники и связи, file roots, размер/доступность оригиналов, повторяющиеся номера и конфликты; разъяснить 245 карточек `raion`, зафиксировать manifest и аномалии без персональных данных/реальных путей в Git.
2. Адаптер **строго с read-only credentials**, без DDL/DML и без инициализирующих legacy-менеджеров. Повторное подтверждение прав учётки до запуска. Все операции меняют **только целевой PostgreSQL и новый document storage**.
3. `source_database + source_entity + source_id` → стабильный target UUID, уникальный mapping и source fingerprint; отдельные `MigrationRun`, `MigrationAttempt`, статистика фаз, ошибки и контроль повторного запуска. Миграция прерывается и возобновляется с контрольной точки без повторного создания карточек/файлов/версий.
4. Сначала справочники и связи с source-qualified идентификаторами, затем типы/реестры/карточки на **существующей схеме ACTI v2 внутри универсального движка**, после — файлы, подписанты и согласующие, исходные реквизиты, права и исходный статус. Не приравнивать исторических исполнителей/подписантов автоматически к доменным пользователям.
5. Файлы копировать потоково с SHA-256, валидацией длины, атомарной публикацией и изолированным storage key; не переносить пользовательские исходные пути в публичный API. `present`, `missing`, `no_path`, `invalid_path`, `inaccessible`, `unknown` — раздельные состояния. Документ без файла остаётся читаемым.
6. **Реестр номеров:** исторические регистрационные номера не перенумеровывать и не выдавать заново. Импортировать происхождение и строковое значение; в книгу регистрации помещать историческую запись лишь по верифицированному правилу сопоставления серии/периода. Дубли и неоднозначные форматы — отдельные явные исключения, не фальшивая уникальность. Перед включением новой рабочей выдачи подтвердить безопасный next-number/high-water или отделённую новую серию.
7. Существующие SQL Server не хранят всей истории версий в формате ACTI v3: **не выдумывать старые редакции**. Для каждой исходной актуальной версии фиксировать provenance, исходный fingerprint и дату, насколько источник позволяет. История нового ACTI начинается с подтверждённой миграции.
8. Миграция очередями/батчами с bounded concurrency и retry: журналы ошибок/пропусков, прогресс в админ-интерфейсе, dry-run, idempotent apply, безопасное возобновление после перезапуска. Не запускать бессистемное одновременное чтение >100 тыс. файлов.
9. Только после импорта/валидирования карточек и файлов — постановка фоновой extraction/indexing из Task 005 с ограничением ресурсов, наблюдаемой очередью и retry. Отсутствие текстового слоя/OCR не считается потерей оригинала.
10. **Проверка целостности**: source→target counts по каждой БД, per-table references, выборочные и агрегированные SHA/size, распределение по статусам и годам, все missing/no_path/unknown, номера и ссылки, ACL, типы, версии, поиск и экспорт. Отчёт без реальных данных в Git. Данные, которые не удалось перенести, фиксировать в перечне аномалий и не скрывать.
11. Новые реальные данные держать отдельно от ранее созданных синтетических fixtures, не загрязнять `okrug`/`raion` пилотными номерами и карточками. План отката — восстановление целевой БД и хранилища из проверенного внешнего backup; исходные SQL Server не затрагиваются.
12. После завершения сохранить исходную ACTI v2 доступной для сверки/чтения. **Не переключать пользователей и не отключать старую ИС автоматически:** переход в рабочую эксплуатацию — отдельное эксплуатационное решение, а не часть технического копирования.

### Автоматическая проверка в браузере

После безопасного dry-run и импорта на целевую ACTI Codex автоматически открывает через HTTPS обе реальные логические коллекции (с разрешённой ролью), проверяет агрегированные счётчики, поиск по номеру/дате/названию, несколько импортированных карточек с оригиналом и несколько случаев без файла, раздельные справочники, связанные акты, журнал номеров и версии/блоки. Просматривает разрешённые реальные документы **без помещения их содержимого в логи или скриншоты Git**. Отдельный viewer не видит недоступные записи; API на записи в SQL Server отсутствует.

**GO/NO-GO без ручного промежуточного тестирования:** Codex самостоятельно проходит проверки и продолжает только при сохранённых и восстановимых backup, достаточном месте, read-only доступе к исходнику, целостном mapping, отсутствии новых критических ACL/файловых ошибок. Если условие не выполнено, прервать опасную фазу и точно сообщить блокер; не форсировать миграцию и не объявлять успешной.

**Критерий результата:** весь доступный корпус и явные исключения учтены, исторические значения и оригиналы сохранены, новые документы/номера/процессы работают в готовой ACTI v3, а исходные SQL Server не изменены.
