# Task 001: проект платформенного ядра ACTI v3

Дата: 2026-10-15. Статус: спецификация согласована пользователем 2026-10-15.

Основание: задание пользователя «ACTI v3 — Task 001: Platform Foundation» и
[дорожная карта](../ACTI_V3_VISION_AND_ROADMAP.md). Roadmap не изменяется.
Этот документ описывает результат реализации, а не утверждает его наличие.

## 1. Назначение и граница задачи

Создать воспроизводимо развёртываемую многопользовательскую web-платформу,
на которой следующие задачи смогут строить реестр документов и процессы.
Критерий завершения: на основной ВМ пользователь входит через браузер,
frontend обращается к защищённому API, схема создаётся миграциями PostgreSQL,
после пересоздания контейнеров учётные записи и аудит сохраняются.

В Task 001 входят локальная идентификация, роли, сессии, API, оболочка UI,
аудит, минимальный событийный контур, файловый провайдер, Compose и контракт
будущего импорта. Реестр, массовый импорт, AD/OIDC, поиск по документам,
конструктор форм, BPM, AI/RAG и внешние интеграции относятся к следующим задачам.
ServiceAccount и его токены пока не нужны: внешний потребитель отсутствует.

Исходные SQL Server `okrug` и `raion`, их файлы и `legacy/v2/` не изменяются.
Количество и состояние исходных документов из задания считаются входными
данными пользователя, а не результатом повторной инвентаризации этой задачи.

## 3. Архитектурное решение

Выбран модульный монолит FastAPI и отдельный React/TypeScript frontend.
Один backend image используется API, мигратором, bootstrap-командой и worker.
Это оставляет общие транзакции и явные границы модулей без распределённой
согласованности и отдельных сервисов для каждой будущей предметной сущности.

Рассмотренные варианты:

| Вариант | Следствие | Решение |
| --- | --- | --- |
| Модульный монолит и небольшой worker | Общие транзакции, простое развёртывание и расширение | Выбран |
| Микросервисы идентификации, аудита, документов | Дополнительные сетевые контракты и эксплуатация без текущей необходимости | Отложен |
| Только каркас API/UI, с памятью процесса вместо постоянных сессий | Не доказывает сохранность и многопользовательскую работу | Не соответствует Task 001 |

```text
Browser -> Nginx HTTPS -> frontend static assets
                      -> /api/v1 -> FastAPI -> PostgreSQL
                                          -> LocalFileStorage
                                          -> Redis
                                  Worker  -> PostgreSQL outbox
                                          -> Redis
```

Состав репозитория:

```text
backend/
  app/api/          HTTP routes, schemas, dependencies, exception mapping
  app/identity/     local credentials, sessions, current actor, role checks
  app/platform/     audit and outbox services
  app/db/           SQLAlchemy models, sessions, transaction boundaries
  app/storage/      StorageProvider and LocalFileStorage
  app/jobs/         minimal outbox worker and its health state
  app/core/         configuration and structured logging
  migrations/      Alembic revisions
  tests/           new platform tests
frontend/src/      auth, shared API client, layout, section availability
deploy/            Compose, images, Nginx, preflight, systemd and runbook
migration/         import contract and synthetic validation examples
docs/architecture/ decisions and acceptance evidence
```

HTTP handlers вызывают прикладные операции; они не управляют файлами напрямую.
Общая проверка аутентификации назначается защищённому API-router. Публичные
health/login маршруты регистрируются отдельно и явно. Новый защищённый route
не должен требовать от автора помнить о добавлении проверки сессии вручную.

Зависимости v3 выбираются независимо от `legacy/v2/requirements.txt`.
Python/FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16+, Redis, React/TypeScript
и средства сборки фиксируются в новых manifests/lockfiles; образы фиксируются
в deployment. Перед реализацией библиотечных API проверяются выбранные версии
и соответствующая документация Context7. Не используются плавающие `latest`.

## 4. Данные, идентификация и доступ

Первичные ключи платформы — UUID; даты операций — UTC `timestamptz`.
Стабильный `User.id` обозначает человека внутри ACTI и не зависит от login,
имени, email, AD или будущих claims OIDC.

| Сущность | Назначение и ограничения |
| --- | --- |
| User | ID, отображаемое имя, активность, даты; отключение немедленно запрещает доступ |
| LocalCredential | Уникальный нормализованный login, user_id, Argon2id hash; отдельна от User |
| Role | Стабильный code; начальные роли admin и user |
| UserRole | Составной уникальный ключ user_id/role_id |
| AuthSession | Hash случайного токена, user_id, CSRF-привязка, срок, отзыв; исходный токен в БД не хранится |
| AuditEvent | ID, время, actor, действие, объект, разрешённые данные события, request ID и источник |
| OutboxEvent | ID, тип/версия payload, объект, payload, время, состояние доставки и попытки |
| ProcessedEvent | Уникальный consumer/event_id и время обработки для идемпотентности worker |

Alembic создаёт таблицы, индексы, ограничения и системные роли на чистой БД.
`create_all()` не заменяет миграции. Единственный migration job выполняет upgrade
до запуска API/worker; ошибка запрещает дальнейший startup. Повторный upgrade
на head безопасен. Параллельный запуск миграторов сериализуется в PostgreSQL.
Приложение не выполняет автоматический downgrade при откате image.

Bootstrap — отдельная CLI-команда в backend image: пароль вводится скрыто,
не передаётся аргументом процесса и не попадает в Compose, Git или логи.
Команда атомарно создаёт первого администратора и событие аудита; повторная
попытка не сбрасывает существующий пароль и не создаёт второго bootstrap-admin.
Публичной web-регистрации и default credentials нет.

Авторизация выдаёт случайный непрозрачный session token. Cookie — HttpOnly,
Secure, SameSite=Lax, Path=/, без Domain. Сессия хранится в PostgreSQL,
имеет абсолютный срок 12 часов; logout отзывает её на сервере. Login создаёт
новую сессию, а не сохраняет предложенный клиентом ID. Токены в localStorage
не используются. Проверяются активность пользователя, отзыв, срок и текущие
роли при запросе. Для изменяющих запросов применяются проверка Origin и
связанный с сессией CSRF token; login принимает только JSON с допустимого Origin.
Локальный dev-режим HTTP задаётся явно и не включается в VM deployment.

Неверный login/пароль и отключённая учётная запись дают одинаковую ошибку.
Login ограничивается по частоте через Redis; заголовки клиента о его адресе
принимаются только от настроенного Nginx. Сбой ограничителя не открывает login.
`401` означает отсутствие действительной сессии, `403` — недостаток права.
Административный platform-status route служит реальным проверяемым примером
права admin; создание полного интерфейса управления пользователями отложено.

Будущий identity adapter сопоставит `(issuer, subject)` с `User.id`.
Прикладные операции получают внутреннего actor и permissions, а не OIDC token.

## 5. HTTP-контракт и наблюдаемость

| Метод/маршрут | Поведение |
| --- | --- |
| GET `/api/v1/health/live` | 200, процесс обслуживает запросы, без проверки БД |
| GET `/api/v1/health/ready` | 200 при доступных БД/Redis/хранилище и ожидаемой Alembic revision; иначе 503 |
| POST `/api/v1/auth/login` | Проверка credentials, создание сессии и аудит; cookie, 200 |
| POST `/api/v1/auth/logout` | Защищённая операция с CSRF; отзыв сессии и очистка cookie, 204 |
| GET `/api/v1/users/me` | Внутренний user ID, display name, роли и CSRF token; иначе 401 |
| GET `/api/v1/admin/platform` | Только admin: обезличенное состояние платформы и версия; иначе 401/403 |

Для ошибок используется `{error: {code, message, details}, request_id}`.
Validation, HTTP errors и необработанные ошибки приводятся к одному формату;
500 не раскрывает stack trace, SQL или параметры подключения.
Request ID проверяется по допустимому формату или генерируется сервером;
возвращается в `X-Request-ID` и записывается в structured logs и аудит.
Health не раскрывает адреса зависимостей, секреты или серверные пути.
OpenAPI описывает cookie auth, статусы, ошибки и публичные исключения;
доступ к Swagger/OpenAPI в VM deployment требует администратора.

AuditEvent записывается в транзакции с успешным изменением. Начальные действия:
bootstrap, login success/failure и logout. Пароли, hashes, cookies и CSRF token
не записываются в аудит/логи. Audit не подменяется outbox или access log.

Для события создания администратора реализуется реальный outbox-путь:
insert в одной транзакции, обработка worker после commit, ограниченные retry,
состояние попытки и времени обработки. Доставка допускает повтор; обработчик
сохраняет receipt с уникальным `(consumer, event_id)` в транзакции обработки.
Первая обработка подтверждает получение platform event, без внешних получателей.
Redis не является единственным хранилищем событий. Worker не запускает импорт
или extraction; его недоступность показывается административным статусом.

## 6. Файлы и происхождение будущих документов

StorageProvider предоставляет `put`, `get/open_stream`, `exists`, `stat` и
`delete_if_allowed`; первое backend-хранилище — LocalFileStorage.
Внутренний storage key непрозрачен для пользователя и не является исходным путём.
Провайдер запрещает обход корня и symlink escape, публикует файл атомарно и
не перезаписывает существующую версию. Тесты используют синтетические файлы.
Операции доступа к будущим документам проходят через backend и его права.
Публичного API загрузки муниципальных документов в Task 001 ещё нет.

Следующий реестр различает Document, неизменяемые DocumentVersion и DocumentFile.
Каждой сущности назначается собственный UUID. Совпадение SHA-256 файлов не
объединяет логические документы. Source ID не становится внутренним первичным
ключом. Номер/дата документа также не являются уникальным идентификатором.

## 7. Контракт будущего импорта

Контракт и синтетический пример размещаются в `migration/`. Полный импорт
не реализуется, целевые Document-таблицы преждевременно не создаются.

Контракт содержит version, source_database (`okrug`/`raion`), source_entity,
source_id, стабильный target_id, исходные реквизиты без потери значений,
source fingerprint, observed_at, run_id, состояние файлов и проблемы проверки.
Ключ соответствия `(source_database, source_entity, source_id)` уникален.
Повтор импорта использует сохранённое соответствие и прежний target_id.
Каждая попытка имеет отдельную историю; изменение fingerprint не создаёт
дубликат карточки. Уникальные ограничения и транзакция обязательны.

Состояния файлов различают present, missing, no_path, inaccessible, invalid_path
и unknown. «Файл не проверен» не считается отсутствием. Проверка/перенос
не изменяет оригинал. Путь источника хранится в закрытом provenance,
не публикуется frontend-у и не используется как целевой storage key.

Предварительное сопоставление проверено по `sqlserver_schema.py`,
`database_sqlserver.py`, `database_common.py` и основным потокам GUI/metadata:

| Поля v2 | Предлагаемая интерпретация | Уровень подтверждения |
| --- | --- | --- |
| documents.id + имя БД | Источник стабильного mapping, а не общий ID двух баз | Однозначно по архивной схеме |
| title, reg_number | Сохранение оригинала; нормализация отдельна | Однозначно по архивной схеме |
| reg_date, published_date, control_date | Строки -> даты после валидации; ошибки сохраняются | Нужны преобразование и профиль фактических значений |
| status_id, type_id, signing_type_id, document_kind_id, theme_id | Справочники с source-qualified IDs и таблицей соответствия | Нужна сверка фактических справочников двух баз |
| executor_id, responsible_executor_id, signers, approvers | Исторические участники документа | Не приравнивать автоматически к пользователям ACTI |
| document_path | Исходная ссылка и отдельно результат проверки файла | Нужны корни источников и безопасное разрешение путей |
| should_publish, removed_from_control | Строки -> нормализованные признаки | Нужен перечень фактических значений |
| created_at, row_version | Время источника и concurrency fingerprint | Часовой пояс DATETIME2 и полнота истории неизвестны |
| number, execution_result, case_number, volume_number, sheets, counts | Сохраняемые исходные реквизиты | Требуют утверждённого семантического mapping перед импортом |

Это анализ сохранённого кода, а не подтверждение равенства живых схем.
До импорта отдельно сверяются `sys.tables`, `sys.columns`, ключи и типы обеих
SQL Server и неоднозначные значения, только через отдельное read-only подключение.
Архивный SqlServerDatabaseManager не используется: конструктор по умолчанию
запускает DDL/seed, а setup_file_storage создаёт каталоги. ApplicationIntent
не заменяет реально ограниченные права source-учётной записи.

## 8. Интерфейс

Русскоязычный UI: страница входа, основная оболочка, боковое меню из восьми
разделов roadmap, верхняя панель с текущим пользователем и logout.
«Моя работа» показывает состояние подключённой платформы и доступные входы,
без выдуманных заданий/документов/показателей. Не реализованные разделы явно
помечены «В разработке». Административный статус доступен только admin.

Единый API client обрабатывает ошибки и request ID. Начальная загрузка `me`,
отправка login/logout, потеря сети и истечение сессии имеют отдельные состояния.
401 переводит на login, 403 показывает отсутствие права; сетевой сбой не
изображается неверным паролем. Повторная отправка формы блокируется на время
запроса. Keyboard navigation, видимый focus и адаптация для узкого экрана
проверяются в браузере. UI не хранит бизнес-правила или DB credentials.

## 9. Развёртывание и сохранность

Compose включает PostgreSQL, Redis, migration job, API, worker и Nginx
со статической сборкой frontend. Снаружи публикуется только Nginx; порты БД,
Redis и API остаются во внутренней сети. API/worker работают без root.

Предварительная проверка сравнивает mountpoint и ожидаемый UUID из закрытой
конфигурации для обоих томов до запуска любого пишущего контейнера.
Bind mount не создаёт отсутствующий каталог автоматически. Данные PostgreSQL,
включая WAL, находятся только на выделенном томе, версии файлов — на документном.
Автоматический startup также проходит проверку: systemd `RequiresMountsFor=`
и ExecStartPre; самостоятельная restart policy Docker не обходит этот барьер.
Автозапуск Docker контейнеров до выполнения preflight не используется.

Перед назначением прав проверяются реальные UID/GID выбранного image; меняется
только назначенный подкаталог на смонтированном томе. Защита underlying-каталогов
и fstab сохраняется. `0777`, `nofail`, форматирование и reboot не применяются.

Секреты и TLS-ключ находятся вне Git в закрытой конфигурации ВМ; пример не
содержит рабочих значений. Nginx использует HTTPS, browser cookie — Secure.
При bootstrap допустим отдельный локальный сертификат с явно настроенным
доверием клиента; он не считается автоматически доверенным. Приватный ключ
не копируется в checkout. Адрес доступа записывается только в локальный отчёт
и сообщается пользователю после действительной браузерной проверки.

Runbook описывает установку, mount preflight, создание секретов, build,
migrations, bootstrap, startup, проверку, restart, backup и restore.
Проверка restore выполняется на отдельной тестовой БД, без подмены рабочей.
Резервная копия на том же сервере не считается независимой резервной копией;
выбор внешнего места хранения остаётся эксплуатационной задачей до реальных данных.

## 10. Проверки и доказательства завершения

| Проверка | Требуемое доказательство |
| --- | --- |
| PostgreSQL | Alembic upgrade на чистой отдельной тестовой БД, повторный upgrade, отсутствие schema drift |
| Bootstrap | Создание admin, повторный запуск без сброса, защита от конкурентного bootstrap |
| Auth | Корректный/неверный login, общая ошибка, cookie flags, истечение/отзыв, disabled user |
| Permissions | 401 без сессии; обычный user получает 403 на admin-route; admin получает 200 |
| CSRF | Запрет неподходящего Origin и изменяющих запросов без корректного CSRF token |
| Health/errors | Live не зависит от БД; ready даёт 503 при потере обязательной зависимости; ошибки имеют request ID |
| Audit/outbox | Запись с транзакцией, отсутствие события после rollback; retry и дедупликация обработки |
| Storage/import contract | Synthetic roundtrip, запрет выхода из корня/перезаписи, квалифицированные source IDs и file states |
| Deployment | Compose config/build/up, контейнеры здоровы, внешних портов PostgreSQL/Redis нет |
| Mount guard | Подставленные неверные ожидаемые UUID запрещают startup; реальные тома не размонтируются |
| Browser | Login -> me/layout -> недоступные разделы -> logout -> повторный отказ защищённого API; ошибки console/network |
| Persistence | Контейнеры пересозданы, admin входит, user ID и audit events сохранились |
| Restore | Dump новой БД восстановлен отдельно; схема и контрольные данные совпали |
| Scope | Git diff legacy/v2 и roadmap пуст; личные настройки и исходные документы не попали в commit |

API/ORM integration tests выполняются на PostgreSQL, а не только SQLite.
Frontend проверяется TypeScript/build и браузером через имеющийся Playwright MCP.
Тесты legacy не выдаются за приёмку v3. Независимые аудиты и многочисленные
ревью не добавляются. Конкретные команды, результаты и SHA реализации
появляются в отчёте приёмки только после фактического выполнения.

Task 001 завершена только после всех относящихся к ней проверок выше.
При отказе критического контура сначала исправляется причина, а статус
развёртывания/приёмки остаётся незавершённым.

Task 002 получает работающую платформу и утверждённые принципы идентификации,
версий и provenance. До переноса реальных документов потребуются подтверждение
живых source-схем, mapping неоднозначных полей, ACL и отдельный контролируемый
план импорта. Следующий этап автоматически не начинается.
