# Task 011 — правила сохранения исторических данных

Дата: 16.10.2026. База проверки кода: main `f224f01`.
Это технический контракт для будущего Task 012, основанный на уже заданных
требованиях единого плана. Он не разрешает запуск миграции, публикацию форм,
выдачу исторических номеров или переключение пользователей.
Task 011 остаётся BLOCKED, Task 012 — NO-GO до отложенных условий эксплуатации.

## Основание и область применения

Закрытый профиль 16.10.2026 охватывает две БД, по 14 таблиц и 65 столбцов,
включая 26 столбцов карточки; все 25 полей встроенной формы учтены.
Фазы профилирования живых источников различались по времени и количеству строк.
Это проверенное покрытие структуры, а не текущий атомарный снимок или импорт.
Параметры подключения, исходные ID, названия документов, имена и пути в Git
не включаются. Исходные данные не исправляются.

Подробности измерений и прав: [TASK_011_SOURCE_READINESS.md](TASK_011_SOURCE_READINESS.md).
Общий порядок: [единый план, Task 012](ACTI_V3_MASTER_TASKS_003_012.md#task-012--финальная-контролируемая-миграция-sql-server-okrug-и-raion).

## Идентичность и номера

1. Ключ происхождения — `(source_database, source_entity, source_id)`.
   Одинаковые числовые ID двух БД обозначают разные записи. UUID назначается
   только целевой транзакцией Task 012 и сохраняется при повторном выполнении.
2. `reg_number` сохраняется исходной строкой: без удаления пробелов, ведущих
   нулей, преобразования в число, дополнений или перенумерации. SQL NULL,
   пустая строка и непустой номер различаются в provenance. Отсутствующий номер
   не генерируется.
3. `number` — номер публикации/газеты; составные строки сохраняются отдельно.
   Его цифры не участвуют в расчёте регистрационного счётчика.
4. Совпадающие номера, заголовки и SHA файлов не объединяют карточки. Повторы
   отражаются отдельными issues; фиктивные уникальные суффиксы запрещены.
5. Предварительные группы по типу/году и числовой MAX не доказывают область
   серии, правила сброса или безопасный next-number. Пока такого доказательства
   нет, исторический номер остаётся реквизитом с происхождением: `NumberEntry`
   не создаётся, счётчики, резервы и отмены не синтезируются.
6. Историческая выдача остаётся заблокированной. Будущая рабочая серия должна
   иметь либо отдельно проверенную границу продолжения, либо доказанно
   отделённую область новой выдачи. Эта политика не включает ни один вариант
   автоматически. Переход сотрудников в новую ИС — отдельное решение.

## Значения и исключения

| Область | Правило |
| --- | --- |
| Заголовок | Сохранить точный текст или NULL. Не заменять NULL выдуманным заголовком и не обрезать текст. |
| Историческая форма | Обычная конфигурация универсального движка на основе 25 полей ACTI v2: `title` остаётся `type="text"`, `system="title"`, с `required=false` и `constraints.max_length=100000`. `textarea` для системного title недопустим. |
| Опубликованные формы | Не переписывать существующие версии. Историческая конфигурация должна быть изолирована от текущего создания документов; при изменении immutable reference binding требуется отдельный обычный тип/набор форм. Новая конфигурация здесь не публикуется. |
| Превышение границы | Значение выше 100000 code points или иной системной границы остаётся явным непринятым исключением с сохранённым raw. Не считать объект успешно перенесённым. |
| NULL и defaults | Передавать исходный NULL явно. В исторической конфигурации убрать подстановки, способные заменить отсутствие значения. NULL, ноль, false и пустая строка не приравниваются. |
| Числа | Не применять округление, clamp или произвольное строковое/числовое приведение. Неверный тип/диапазон — issue; raw сохраняется. |
| Boolean | Для наблюдавшихся точных строк: `Да`/`1.0` → true, `Нет`/`0.0` → false, `Не указано`/SQL NULL → null. Другой литерал — issue и отсутствие нормализованного значения. Не применять truthiness, свободный numeric cast или догадки регистра. |
| Календарные даты | Только явно проверенные грамматики ISO `YYYY-MM-DD`, `DD.MM.YYYY` и подтверждённый ISO datetime; проверять существование даты. Для календарного реквизита не сдвигать день через UTC. Raw сохраняется полностью. |
| Неразобранная дата | Нормализованное значение NULL плюс issue с закрытым raw. Не угадывать locale, не заменять epoch/current date и не исправлять источник. |
| `datetime2` | Сохранить исходное значение и SQL scale/precision; неизвестный timezone остаётся неизвестным. Не присваивать зону VM или UTC. UTC используется для нового `observed_at` и аудита переноса. |
| `row_version` | Непрозрачные байты с точным lossless encoding; это fingerprint input, а не дата/время. |
| История | Не выдумывать прежние версии, авторов и операции. Legacy timestamps не заменяют новый аудит ACTI. |

Поздняя проверка подтвердила пять заголовков длиннее 1000 Unicode code points,
максимум 1967, и 71 NULL-заголовок. В профиле также есть 1357 NULL страниц,
66541 NULL приложений и одна неразобранная непустая дата публикации.
Это исторические наблюдения; перед Task 012 их надо пересчитать. Все новые
аномалии учитываются по тем же правилам, а не теряются ради совпадения счётчиков.

Справочники разделены по источнику и сущности. Исполнитель, ответственный,
подписант и согласующий остаются `ReferenceItem`; совпадение имени не создаёт
User, AD-link, сессию или разрешение. Один SHA не объединяет логические файлы.

Текущая модель требует уникального label внутри `ReferenceSet`. В сохранённой
метадате источников у всех 20 справочников есть действующий unique index по
`name`. Это доказательство для данной фазы, не гарантия будущего состояния.
Существующие seed/custom items целевой ACTI не следует автоматически принимать
по совпадению label: они могут не иметь того же происхождения. Для истории
использовать изолированные source-qualified наборы и обычные explicit bindings
исторической конфигурации. Проверить целевые коллизии до записи; не сливать
личности и не менять ограничения универсального справочника ради импорта.
Существующие document/registry/field ACL сохраняются; исторические участники
не являются источником новых разрешений.

## Оригиналы и закрытое происхождение

Шесть состояний различаются: `present`, `missing`, `no_path`, `inaccessible`,
`invalid_path`, `unknown`. Строка пути не подтверждает `present`; требуются
успешное чтение/копирование и SHA/size. Unknown не превращается в missing.
Карточка без оригинала остаётся читаемой; фиктивный `DocumentFile` не создаётся.
Состояние и аномалия сохраняются в миграционном/provenance-контракте, поскольку
текущая модель `DocumentFile` отдельного `file_state` не имеет.

Raw SQL fields, исходные пути, точные timestamp/bytes и junction provenance
хранятся в закрытом контракте Task 012, отдельно от публичных метаданных API.
Не помещать исходный путь в публичный `custom_data`, URL или storage key.
`source_fields` и нормализованные значения сверяются раздельно; сериализация
не должна округлять Decimal/datetime2 или терять тип/пустоту/байты.

## Проверка технического контракта — PASS

Закрытая проверка `historical-policy-technical-acceptance-20261016.json`
сопоставила все **130/130** столбцов сохранённой метадаты с полным mapping:
пропусков и повторных правил нет. Подтверждены 20 действующих unique name
indices в тех же сохранённых фазах источников.

На неизменённом backend main `f224f01` выполнен **21 in-memory сценарий**:
обычная историческая схема проходит `validate_schema`; NULL, пустой текст,
1967/100000 code points, non-BMP Unicode, исходный номер с пробелами/нулями,
nullable Boolean/числа сохраняются. Превышение длины/числовой границы,
строковый Boolean, недопустимый тип и несуществующая дата отклоняются.
Прежняя встроенная форма по-прежнему отклоняет NULL/1001-символьный title,
её определение не менялось.

Это проверка существующих валидаторов и структурного покрытия. Соединений
с источниками, DB writes, опубликованных схем и присвоенных source UUID — 0.
Она не доказывает исполненный импорт, сохранение в PostgreSQL или browser E2E
будущей исторической конфигурации; эти проверки относятся к Task 012.

- Снять новый read-only manifest, проверить PK/FK/unique constraints, права
  читателей, полное покрытие столбцов и изменение watermarks. Сохранённые фазы

- Для каждого обработанного объекта иметь mapping/run/attempt/fingerprint
  и результат. При повторе не создавать новую логическую карточку из-за
  совпадающего номера или изменившегося содержимого.
- Сверить нормализованные значения и закрытый raw, NULL/пустоты, распределения
  аномалий, исходные строки номеров и file SHA/size по каждой БД отдельно.
- Проверить историю/справочники/поиск/экспорт и запреты доступа реальным HTTPS
