# Document workspace

The working documents page uses one persisted layout state: `table`, `split` (default), or `card`. The same result table and DocumentCard stay mounted while panes are hidden, preserving card drafts and tabs. Layout preferences are scoped to the authenticated user and editor/viewer workspace. Search parameters, selected document and cursor remain owned by Documents; layout changes do not submit a search. Each pane retains scroll positions for each layout.

Click selects a row; double-click or Enter opens the full card. Arrow keys, Home and End select rows. The three-position control supports arrow keys, Home and End. Collapsed rails return to the split layout; the card's return action restores the preceding list layout. Below 650px all layouts stack the independently scrolling panes and collapsed rails vertically. The expanded table scrolls horizontally inside its pane.

The table has seven presentation columns. Title, registration number/date and document type use existing ACL-filtered search summaries. The three optional business columns resolve against each document's immutable published schema: an exact normalized list-view column label is an explicit alias; otherwise an unambiguous field label is used. No legacy keys are inferred. Missing, inaccessible, condition-hidden or unresolved values render as an em dash. Identity and reference values require resolved display values; raw identifiers are not a display fallback.

Standard sortable headers use the existing search API. Configured columns support sorting only when a single document type is selected and all its loaded published schemas map the column to the same unconditional, filterable scalar field. This avoids sorting one schema version's values while presenting another version's different field. Existing form configuration, filter controls and configured export columns retain their contracts. No API, database migration, numbering or document revision contract changes are required.

The separator resizes panes with pointer capture, including dragging back out of a collapsed layout. A list fraction at or below 8% selects `card`; at or above 92% it selects `table`; intermediate widths select `split`. The last split fraction persists in the existing user/workspace preference, so older preferences without a fraction still use 35/65. Collapsed-rail clicks and the three-position switch preserve that fraction. The separator supports Left/Right (Up/Down on narrow screens), Shift for larger steps, Home/End for full modes and Escape/pointer cancellation to restore the drag's initial layout. It remains mounted across mode changes, as do both panes and the card draft. Resizing anchors the first visible document through row reflow; cancellation restores the initial scroll offsets as well as the layout. Events from another pointer cannot terminate the captured drag.

The compact list always presents title, registration number and registration date. CSS container queries expand the same table as the list pane grows: document type at 620px, kind at 780px, topic at 940px and responsible person at 1100px. These are pane widths, independent of viewport or layout names. Published schemas are available whenever the list is visible, so configured columns remain populated during resizing. Existing per-version field redaction and sorting constraints still apply.

Search is an initially expanded disclosure. Closing it hides its mounted inputs, saved views and grouped `Экспорт и импорт` disclosure without changing the applied query, results or card draft. That transfer group contains the existing CSV/XLSX export actions; it does not introduce a document-import API. Sort controls and the single layout switch form a compact strip directly above the two panes and remain available when search is closed. Compact row metadata carries explicit number/date captions and remains stacked at very narrow pane widths.

`Все реестры` sends an empty `registry_ids` list, meaning all registries permitted by the existing server ACL query. It is not a request to choose one registry first. The page only shows the no-access message when the returned registry list contains no readable registry. Missing registration metadata remains an em dash; the UI never substitutes creation dates or reads hidden form values as a fallback.
