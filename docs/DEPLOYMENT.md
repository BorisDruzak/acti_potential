# ACTI v3: развёртывание платформенного ядра

## Контракт среды

Основная машина и UUID заданы только в `project.local.toml` и локальном контексте.
Все команды этого документа выполняются на предназначенной для ACTI Ubuntu VM.
SQL Server и источники документов не используются при запуске платформы.

Нужны Docker Engine/Compose, Python 3 для preflight и два подтверждённых тома:
`/srv/acti/postgresql` и `/srv/acti/documents`. Не использовать `nofail`, fallback
на ОС, `0777`, форматирование или reboot. Перед любым запуском сравнить UUID с
локальным контрактом, а не просто проверить наличие каталога.

## Подготовка

1. Установить Docker и Compose из согласованного источника пакетов Ubuntu,
   проверить `docker version`, `docker compose version`. Не переносить настройки
   или адреса другой машины. Установка сервиса не требует reboot этой задачи.
2. Выбрать committed release; `git archive <SHA>` передать на ВМ и распаковать
   в отдельный root-owned release directory. Сохранить предыдущий release.
   Не включать `.local`, `.env`, local context, ключи и документы в archive.
3. Из выбранных images проверить UID/GID PostgreSQL (`id postgres`) и ACTI
   (`id` backend image; задан 10001:10001). После проверки UUID создать только
   назначенные подкаталоги: `postgresql/data`, `postgresql/test` (если нужны tests)
   и `documents/objects`, назначить им фактического владельца сервиса.
4. Создать root-owned `/etc/acti-v3/runtime.env`, mode 0600, по
   `deploy/.env.example`. Пароли и session secret генерировать случайно и хранить
   вне checkout. Указать полный release path, его source SHA, действительный
   HTTPS origin и UUID обоих томов. Никаких встроенных рабочих секретов нет.
5. Для production PostgreSQL задать разные случайные `POSTGRES_PASSWORD`,
   `ACTI_OWNER_PASSWORD`, `ACTI_APP_PASSWORD`. Migration URL использует
   `acti_owner`, app URL — `acti_app`. Init SQL создаёт роли только на чистой БД.
   Существующая БД не переинициализируется при restart; смена env-пароля сама
   по себе не изменяет пароль уже существующей роли.
6. Разместить server.crt, server.key и ca.crt в `/etc/acti-v3/tls`; ключ mode
   0600, каталог 0700. SAN должен включать фактическое имя/адрес и localhost
   для внутреннего TLS healthcheck. Для первого запуска допустим локальный CA:
   доверять только проверенному публичному сертификату CA на нужных клиентах.
   CA private key остаётся закрытым на ВМ. Не использовать отключение TLS
   проверки в качестве приёмки. Следить за сроком сертификата, автоматическое
   продление пока не настроено.
7. Поддерживать `deploy/images.lock.env`: зафиксированы публичные digest images.
   Backend base также закреплён digest, Python/npm зависимости — lockfiles.

## Build и запуск

```sh
sudo sh -c 'set -a; . /etc/acti-v3/runtime.env; set +a; python3 "$ACTI_RELEASE_DIR/deploy/preflight.py"; docker compose --env-file "$ACTI_RELEASE_DIR/deploy/images.lock.env" --env-file /etc/acti-v3/runtime.env -f "$ACTI_RELEASE_DIR/deploy/compose.yaml" config --quiet; docker compose --env-file "$ACTI_RELEASE_DIR/deploy/images.lock.env" --env-file /etc/acti-v3/runtime.env -f "$ACTI_RELEASE_DIR/deploy/compose.yaml" build'
```

Установить `deploy/stack.sh` в `/usr/local/sbin/acti-v3-stack` root:root 0755,
а `deploy/acti-v3.service` — в `/etc/systemd/system/` root:root 0644.
Затем `sudo systemctl daemon-reload` и `sudo systemctl enable --now acti-v3`.
Сервис требует оба mount unit и выполняет UUID preflight до Compose.
Самостоятельный Docker restart контейнеров отключён, чтобы не обойти проверку
при старте Docker. После аварийного завершения контейнера оператор проверяет
причину и выполняет `sudo systemctl restart acti-v3`; постоянного внешнего
мониторинга и high availability Task 001 не добавляет.

Порядок: PostgreSQL ready -> migration success -> API/worker -> frontend.
Мигратор сериализуется advisory lock, выполняет Alembic upgrade и выдаёт app
роль только DML-права, без superuser/DDL. Audit допускает INSERT/SELECT,
но не UPDATE/DELETE ролью приложения. Ошибка migration блокирует API/worker.
Compose не публикует PostgreSQL, Redis или API; доступны только HTTPS и HTTP
redirect Nginx. Проверить внутреннюю Docker subnet и задать её в закрытом
`ACTI_TRUSTED_PROXY_CIDRS`, затем пересоздать API. Nginx заменяет X-Real-IP,
а backend принимает его только от настроенного proxy; заголовок внешнего
клиента сам по себе не меняет адрес rate limiter.

## Первоначальный администратор

Выполнить bootstrap в API-контейнере через интерактивный terminal:

```sh
sudo sh -c 'set -a; . /etc/acti-v3/runtime.env; set +a; docker compose --env-file "$ACTI_RELEASE_DIR/deploy/images.lock.env" --env-file /etc/acti-v3/runtime.env -f "$ACTI_RELEASE_DIR/deploy/compose.yaml" exec api python -m app.identity.bootstrap'
```

Команда спрашивает login, имя и пароль (не менее 14 символов), подтверждение
скрыто. Не передавать пароль argv, не записывать его в shell history или Git.
Bootstrap атомарен и не сбрасывает существующую учётную запись при повторе.
После Task 002 локальные пользователи создаются в `/admin` → «Пользователи».
Администратор задаёт первоначальный пароль минимум из 14 символов и передаёт
его по защищённому каналу. До обязательной смены пароля доступ к данным закрыт.
Смена пароля обновляет cookie/CSRF; сброс пароля и блокировка отзывают сессии.
Повторный bootstrap для обычных пользователей не нужен. AD/OIDC отсутствуют.

Task 002 добавляет `0002_schema_engine` и повторяемое создание конфигурации
ACTI v2, сохраняя учётные записи и сессии. Реестры «Округ»/«Район» изначально
не дают доступ к содержимому даже администратору: действия выдаются отдельно
в `/admin` → «Роли и доступ». Роль `user` совместима с редактором. Настоящие
справочники и документы SQL Server при запуске не импортируются.

Task 003 добавляет совместимую миграцию `0003_reference_details`: описания
справочников, коды/порядок/иерархию/даты значений. Существующие UUID, provenance,
карточки, версии, учётные записи и сессии сохраняются. Перед активацией обязателен
штатный backup; downgrade рабочей БД для отката image не выполнять.
Новых environment variables, внешних сервисов и подключений SQL Server нет.

CSV/XLSX экспорт документов использует те же серверные фильтры и ACL, что список.
Ограничения запроса: 10 000 строк, 16 MiB текстовых значений, 32 767 символов
в одной ячейке; при превышении API возвращает ошибку, без усечения данных.
Условно скрытые поля недоступны для поиска/сортировки, разрешённые значения
могут экспортироваться согласно текущим правам строки и версии схемы.
Справочники импортируются/экспортируются администратором пакетами до 2 000
строк; импорт ограничен 2 MiB файла и 16 MiB распакованного XLSX. Формулы
при импорте отклоняются; CSV защищает формулы префиксом, XLSX хранит текстовые
ячейки, сохраняя ведущие нули. Сохранённые поиски хранятся в браузере отдельно
для пользователя, режима и реестра; между устройствами не синхронизируются.

Task 004 добавляет `0004_number_register`: отдельную книгу номеров, счётчики
периодов, права, записи и журнал операций. Мигратор ограничивает app-role:
идентичность номера защищена триггером; операции и receipts идемпотентности
не обновляются и не удаляются. Присвоение требует права на серию и карточку,
проверяет revision и ограничения опубликованной формы. Старые строки ACTI v2
не получают новую нумерацию автоматически. До контролируемой миграции доступны
только отдельные синтетические серии; исторические `okrug`/`raion` и ACTI v2
для выдачи закрыты. Новых environment variables или служб задача не добавляет.
Проверка обновления включает повтор запроса, параллельное резервирование,
неповторную выдачу отменённых номеров и сохранение счётчика после штатного restart.

Task 005 добавляет `0005_content_search`: extraction, неизменяемые структурные
блоки, фрагменты метаданных и состояние индекса; миграция включает trusted
extension `pg_trgm` и GIN-индексы русского FTS. Роль мигратора остаётся владельцем
целевой БД; app-role не получает DDL или изменение блоков. Индекс метаданных —
производные данные, его фрагменты worker может перестраивать; старые оригиналы,
номера и опубликованные схемы не изменяются.

Backend image закрепляет `pypdf` через `uv.lock` и `antiword=0.37-16` для DOC.
Новых служб и environment variables нет. Worker использует тот же защищённый
том оригиналов с read-only bind, лимиты 768 MiB / 1 CPU / 64 процесса и прежнюю
закрытую Docker-сеть. Дочерний парсер получает байты через stdin без секретов
окружения, с отдельными ограничениями памяти, CPU, времени и объёма результата.
При недоступном оригинале/таймауте действуют ограниченные retry/backoff и lease;
зависшее после прерывания состояние восстанавливается. Повреждённые и защищённые
файлы имеют явный статус; OCR не установлен. Права на документ/файл/поле всегда
проверяются заново; изменение метаданных временно исключает устаревшие фрагменты
до актуализации индекса.

Бинарный DOC поддерживается в пределах возможностей закреплённого `antiword`:
содержание извлекается как текст, без сохранения оформления. Корректные OLE DOC
с коротким потоком WordDocument, который converter не поддерживает, получают
`unsupported / legacy_doc_short_stream`, а не признак повреждения. Ограничение
подтверждено в [исходнике antiword 0.37-16](https://sources.debian.org/src/antiword/0.37-16/wordole.c/).
Оригинал остаётся доступен по ACL; для извлечения можно добавить DOCX или цифровой
PDF новой версией. При изменении поведения parser fingerprint меняется, прежние
результаты и блоки не перезаписываются.

## Связи документов

Task 006 добавляет миграцию `0006_document_relations`, таблицы `document_relations`
и `relation_events`. Новых сервисов, внешних API, credentials или переменных
окружения для связей не требуется. Применение выполняется существующим migrate
перед запуском API/worker после штатного backup и проверки mount/UUID.

Право `confirm_relations` назначается явно в доступе к реестру и, если карточка
ограничена индивидуальным ACL, также в её разрешениях. Для предложения связи
нужно изменение обоих документов; для подтверждения/отклонения дополнительно
нужно это право на обе стороны. Администратор конфигурации не получает доступ
к содержимому автоматически. Версия/блок основания требуют текущего разрешения
на скачивание и доступности соответствующего поля файла.

Предложения, подтверждения и отклонения сохраняют audit/outbox; исходные
документы и их реквизиты не перезаписываются. Подтверждённое решение нельзя
редактировать или удалить через приложение. Будущие даты и связи с прежними
версиями остаются в истории; текущие основания статуса вычисляются отдельно
по разрешённым подтверждённым связям. Внешний источник — проверенная автором
HTTPS-ссылка с реквизитами/версией/датой; ACTI не загружает его содержимое.

## Описания процессов

Task 007 добавляет `0007_process_knowledge` и шесть таблиц: `processes`,
`process_versions`, `process_steps`, `process_transitions`, `process_step_sources`,
`process_step_templates`. Дополнительные сервисы и переменные среды не нужны.
Миграция применяется существующим migrate после backup и mount/UUID preflight.

Каждый процесс относится к реестру. Его чтение требует явного доступа к этому
реестру; настройка и публикация дополнительно требуют роли администратора и
права изменения. Черновики доступны только администратору с этими правами.
Опубликованные версии и их дочерние записи защищены от изменения триггерами
PostgreSQL; новая редакция создаётся отдельно. Дата действия и номер версии
определяют описание на выбранную дату; будущая версия не становится текущей
досрочно. Метаданные процесса также фиксируются в опубликованной версии.

Шаг ссылается на конкретную опубликованную форму и точные версии/блоки документов.
Текущие ACL источника проверяются при публикации и при каждом чтении основания;
закрытый источник заменяется отметкой без идентификаторов, реквизитов и текста.
Правила переходов декларативны, проверяются по заданному порядку до первого
совпадения, затем используется явный «иначе». Предпросмотр не выбирает маршрут
по закрытому полю или отсутствующему обязательному значению. В этом этапе
хранятся описания, без создания экземпляров исполнения или внешних согласований.
Одна версия ограничена 200 шагами и 500 переходами; текущий каталог выдаёт
до 1000 процессов. Для большого каталога перед масштабным использованием
потребуется пагинация в рамках стабилизации API.

## Шаблоны и практика

Task 008 добавляет миграцию `0008_knowledge` и таблицы `knowledge_templates`,
`knowledge_template_versions`, `practice_cases`, `practice_links`,
`knowledge_curations`, `knowledge_usage`. Новые сервисы, зависимости и переменные
среды не требуются. Перед штатным migrate обязательны backup и mount/UUID preflight.

Объекты относятся к реестру и имеют видимость «реестр» либо «личное» (владелец
и автор). Опубликованное содержание и основания неизменяемы; новую редакцию
шаблона создают отдельно. Видимость и архивирование меняются отдельным действием
с причиной, без перезаписи опубликованной версии. Право `curate_knowledge`
назначается явно вместе с правом изменения: оно разрешает подтверждение,
рекомендацию и снятие рекомендации. Администратор не обходит ACL содержания.

Оригинал шаблона закрепляет точную существующую версию файла. Скачивание и поиск
по извлечённому содержимому требуют как прав шаблона, так и текущих прав исходного
файла; закрытые основания не раскрывают реквизитов. Характеристики связанной формы
проверяются и выдаются с её типами, справочниками и доступом к полям. Привязки
`template_versions` в шагах дополняют прежние файловые шаблоны и фиксируют версию.

Метрики — суточные счётчики действий по объекту и реестру, без пользовательских
профилей, поисковых запросов и IP. Их просмотр требует права куратора и учитывает
текущую видимость объектов. Каталог ограничивает область подбора 10 000 объектов;
при превышении нужно уточнить фильтр. Это ограничение следует учитывать до
масштабного наполнения, при стабилизации API.

## Исполнение процессов

Task 009 добавляет миграцию `0009_execution`, таблицы `execution_instances`,
`step_executions`, `step_results`, `execution_checklist`, `execution_events`
и API `/api/v1/execution`. Новых сервисов и переменных среды не требуется.
Миграция применяется штатно после backup и проверки обязательных mount/UUID.

Старт требует прав чтения/создания в реестре опубликованного процесса.
Исполнитель — активный редактор с текущими правами чтения/изменения.
Назначенный исполнитель ведёт шаг; создатель или исполнитель управляет
экземпляром в пределах права изменения. Администратор конфигурации не получает
доступ к чужому содержимому автоматически. Список и история проверяют текущие
права, основания и результаты дополнительно проверяют исходные документы/поля.
Когда маршрут зависит от закрытого поля, его конкретные этапы и история скрыты.

Snapshot сохраняет опубликованную модель, схемы и точные ссылки оснований/
шаблонов на момент старта. Позднейшие редакции конфигурации не меняют исполнение.
Результат хранит подтверждённые значения и точные ссылки на документы/файлы;
реквизиты документа подтверждаются отдельно по metadata revision, которая
не совпадает с номером файловой версии. Завершённые попытки, результаты и
события неизменяемы. Возврат с причиной создаёт новую попытку предыдущего шага.
Переход выбирается на сервере по сохранённому результату и закреплённым правилам;
клиент не задаёт произвольный следующий шаг.

Сроки — UTC. Просрочка вычисляется при чтении по часам сервера; отдельный worker
или планировщик не нужен. Явный прошедший срок требует причины. Для проверки
просрочек не менять часы ВМ. После штатного перезапуска проверить те же UUID,
результаты и историю экземпляра через HTTPS; один health не доказывает сохранность.

## Сервисный API и эксплуатационные показатели

Task 010 добавляет миграцию `0010_service_api`: сервисные идентичности и хеши
токенов, суточные агрегаты API и временные bookmarks событий. Новых сервисов,
внешних моделей или переменных среды не требуется. До migrate выполнить
штатные backup и mount/UUID preflight. Bookmarks имеют ограниченный срок жизни;
их очистка и повторы outbox выполняются существующим worker.

Миграция также добавляет сохраняемый порядок публикации outbox и заполняет его
для прежних обработанных событий. Новый worker назначает следующие номера
под транзакционной блокировкой; внешний feed не зависит от времени создания
транзакции. Штатный systemd restart останавливает прежний stack перед migrate
и запуском новых API/worker. Не выполнять rolling-замену с одновременной работой
старого publisher: он не назначает новый номер публикации. Для отката образов
проверять совместимость worker и схемы отдельно; schema downgrade автоматически
не выполняется.

Сервисный API `/api/service/v1` находится вне пользовательского cookie API.
Для интеграции администратор явно задаёт реестры, операции чтения и срок токена.
Секрет выдаётся один раз, в БД сохраняется хеш. При ротации старый токен отзывается;
отключение сервисной записи отзывает её токены. Для повторного подключения
нужно выдать новый токен. Не добавлять секреты в конфигурацию фронтенда,
URL, отчёты, shell history или диагностические снимки.

Сервисные пользователи имеют стабильный UUID и текущие ACL, но не локальный
пароль. Управлять ими следует в разделе сервисных записей. Прежние интерактивные
пользователи, роли, CSRF и сессии продолжают работать через `/api/v1`.
Контракт потребителя и правила точных версий приведены в
`docs/api/KNOWLEDGE_SERVICE_V1.md`.

Панель эксплуатации показывает разрешённые агрегаты: API/поиск и время открытия,
использование знаний/процессов/номеров, состояния очереди и ошибки извлечения.
Нет поисковых текстов, IP и пользовательских профилей. Операторский повтор
ошибки требует причины и не должен обходить текущую область доступа.
После deploy проверить выдачу/ротацию/отзыв через UI и независимым API-клиентом,
старую ссылку на блок после отзыва прав, а также обычные admin/editor/viewer
сессии и сценарий ACTI v2. Health не заменяет эти проверки.

## Проверка и перезапуск

- `sudo /usr/local/sbin/acti-v3-stack status`: PostgreSQL/Redis/API/worker/frontend
  здоровы, migrate завершился с кодом 0.
- Через HTTPS проверить `/api/v1/health/live` и `/api/v1/health/ready` (200),
  а `/api/v1/users/me` без сессии (401). Live не доказывает готовность БД.
- В браузере войти, проверить пользователя, навигацию, admin status и выйти.
  Проверить `/admin` (конструктор, справочники, пользователи и доступ), `/work`
  (карточки и версии) и `/view` (просмотр без действий изменения).
- Перед `sudo systemctl restart acti-v3` записать контрольный user ID и счётчики
  аудита без credential material, затем сравнить их и повторить вход.
- Данные находятся в bind mounts, `down --volumes` и удаление data path не нужны.
- Health/логи/request ID не должны раскрывать credentials, cookie, SQL или paths.
  Не выгружать полные `docker inspect`/`compose config` с секретами в отчёты.

## Backup и restore test

`sudo sh <release>/deploy/backup.sh` проверяет UUID и создаёт custom-format dump
в закрытом backup-подкаталоге PostgreSQL-тома. `restore-test.sh <dump>` создаёт
только фиксированную БД `acti_restore_test`, отказывается использовать уже
существующую БД с этим именем, восстанавливает dump и выводит revision, digest
набора user IDs и число audit rows для live/test БД. После проверки удаляет
только созданную им disposable БД; рабочая БД не перезаписывается.
Выводы должны совпасть при отсутствии новых audit-записей в это время.
Скрипт требует доступного свободного места под вторую БД на том же томе.

Два тома одной ВМ и backup на той же ВМ не являются независимой резервной копией.
До загрузки реальных документов назначить внешний backup destination,
retention, расписание и регулярно проверяемое восстановление. Версии оригиналов
требуют согласованной копии document storage вместе с БД.

## Обновление и откат

Сделать backup, подготовить новый root-owned committed release и images,
проверить его конфигурацию, обновить закрытые release path/source SHA и
перезапустить systemd. Записать фактический image/source SHA и health/browser
результаты. При сбое сохранить логи с redaction, исправить причину и повторить
проверку. Откат image не выполняет schema downgrade: совместимость миграции
и старого кода проверяется до выбора такого отката. Нельзя восстанавливать
поверх рабочей БД без отдельного контролируемого плана восстановления.

## Разработка и tests

Backend: `uv sync --frozen`; отдельная PostgreSQL БД с суффиксом `_test` на
выделенном томе и отдельная Redis DB. `uv run pytest -q`,
`uv run ruff check app tests`, `uv run alembic check`.
Destructive fixture отказывается работать с именем без `_test`.
Frontend: `npm ci`, `npm test -- --run`, `npm run typecheck`, `npm run build`.
Фактическая приёмка хранится отдельно в `docs/architecture/TASK_001_ACCEPTANCE.md`;
команды этого runbook сами по себе не означают выполненную приёмку.


## SEARCH-001

Миграция `0012_search_retrieval` добавляет компактные карты источников chunks,
версию производного индекса и один btree fingerprint для нормализованных номеров.
Индекс обоснован EXPLAIN на синтетическом корпусе: прежние FTS/trigram не могут
ответить на сравнение номеров без пунктуации. Хеш всегда дополняется точным
сравнением, поэтому коллизия не создаёт совпадение. Имеющиеся GIN не дублируются.

Перед миграцией обязательны штатные backup и mount/UUID preflight. Старые
оригиналы, карточки, номера и опубликованные формы не перезаписываются. Существующий
worker пакетами обновляет metadata index и карты прежних completed extractions;
состояние доступно в «Эксплуатация» → «Поисковый индекс». Администратор с read
и update конкретного реестра может запросить фоновую перестройку с причиной.
Право администратора само по себе не открывает закрытое содержимое.

Необязательные `ACTI_SEARCH_WEIGHTS` и `ACTI_SEARCH_SYNONYMS` — JSON в защищённом
runtime.env; `null` оставляет встроенные значения. Веса находятся в [0,1], словарь
ограничен 32 группами по 2–8 выражений. `ACTI_SEARCH_ALGORITHM_VERSION` по
умолчанию `lexical-2`. Изменение профиля сбрасывает старые поисковые курсоры.
Новых внешних сервисов, SQL Server действий, OCR/LLM/vector-зависимостей нет.
