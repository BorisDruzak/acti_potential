# Контракт будущего импорта

Карточки контролируемого импорта получают отдельный статус карточки `published`
и место публикации `["internal"]` через `migration.defaults.legacy_card_defaults`.
Это не меняет исторический статус правового акта и не публикует карточку в общей
базе: `shared` выбирается отдельно уполномоченным редактором. При реальном импорте
эти целевые атрибуты записываются в той же транзакции, что mapping и история.
Миграция PostgreSQL применяет тот же статус только к уже импортированным записям
с идентичностью `okrug`/`raion`, `source_entity=documents`; источники не изменяются.

Task 001 создаёт контракт, а не исполняемый импорт. Исходные SQL Server и файлы
остаются неизменными. JSON Schema v1 и пример содержат только синтетические данные.

Mapping уникален по `(source_database, source_entity, source_id)`. Один ID в
`okrug` и `raion` обозначает разные исходные карточки. Будущий importer сначала
создаёт/находит mapping в целевой транзакции с unique constraint и сохраняет
его UUID `target_id` при повторном запуске. Номер документа и SHA файла не
заменяют этот ключ. Document, DocumentVersion и DocumentFile имеют разные UUID;
файл версии неизменяем, совпадение файлов не объединяет логические карточки.

Каждый run/attempt хранит время, source fingerprint, результат и перечень
проблем. Исходные реквизиты сохраняются без потери значений; нормализованное
значение существует отдельно. Повтор с новым fingerprint создаёт новую запись
истории, а не дубликат карточки. Историю следует записывать даже для пропуска
неизменившегося источника. Схема будущих mapping/run/attempt таблиц реализуется
в контролируемой задаче импорта вместе с реестром; Task 001 их не симулирует.

`present`, `missing`, `no_path`, `inaccessible`, `invalid_path`, `unknown`
различаются. Unknown не является missing. Source path остаётся закрытым
provenance, не становится storage key и не выдаётся frontend-у. Реальные
метаданные/пути/документы не добавляются в примеры или отчёты Git.

Предварительное сопоставление по сохранённому `legacy/v2/src/sqlserver_schema.py`
и `database_sqlserver.py` (живые схемы в Task 001 не исследовались):

| Источник | Назначение | Что ещё проверить |
| --- | --- | --- |
| id + имя БД | Source-qualified mapping | Реальные PK обеих баз |
| title, reg_number | Исходные заголовок и номер | Сохранение null и оригинального текста |
| reg_date, published_date, control_date | Даты после преобразования строк | Форматы, ошибки, неоднозначные значения |
| status_id, type_id, signing_type_id, document_kind_id, theme_id | Справочники через mapping | Фактические значения и различия двух БД |
| executor_id, responsible_executor_id, signers, approvers | Исторические участники | Не приравнивать автоматически к User |
| document_path | Источник файла и отдельный file_state | Корни, относительные/абсолютные пути, доступность |
| should_publish, removed_from_control | Нормализованные признаки | Фактические строковые значения |
| created_at, row_version | Provenance времени и fingerprint | Часовой пояс, полнота/ограничения истории |
| number, execution_result, case_number, volume_number, sheets, counts | Исходные реквизиты | Семантика и будущая типизированная модель |

Перед реальным импортом отдельно проверить `sys.tables`, `sys.columns`, типы,
ключи и агрегированный профиль значений только учётной записью с read-only
правами. Не создавать архивный SqlServerDatabaseManager: его конструктор
по умолчанию запускает DDL/seed, а файловый mixin создаёт каталоги.
ApplicationIntent сам по себе не гарантирует запрет записи. Подтверждение
mapping, ACL, план переноса и проверка внешних резервных копий обязательны до
переноса реального корпуса; автоматически следующий этап не начинается.
